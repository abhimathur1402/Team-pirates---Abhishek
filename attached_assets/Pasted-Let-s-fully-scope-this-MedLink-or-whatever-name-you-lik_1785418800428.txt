Let's fully scope this — "MedLink" (or whatever name you like): a real-time emergency resource matching network for beds, ICU slots, and blood units across hospitals.

The core idea

Hospitals are silos. When a patient needs an ICU bed or a rare blood type right now, staff manually call around — 20 minutes on the phone while a patient waits. Your system replaces that with: hospitals broadcast live inventory → an algorithm finds the nearest compatible match → dispatches it instantly, like Uber matching a rider to a driver, but for beds and blood.

This is a strong hackathon pick because the "smart" part is a real algorithm (graph search + constraint matching), not a black-box model, so you can explain exactly why a match was chosen — judges love that transparency.

The algorithm (this is your "wow" — be ready to explain it on stage)

This isn't classification, it's constrained nearest-match search:

Filter step (hard constraints) — from the pool of hospitals, keep only those where:
Resource type matches (ICU bed / blood type, with blood compatibility rules like O- is universal donor, AB+ universal recipient)
Quantity available ≥ requested
Hospital is operational/reachable
Ranking step (soft scoring) — among valid candidates, rank by a weighted score:
   score = w1*(1/distance) + w2*(inventory_freshness) + w3*(hospital_capacity_headroom) - w4*(traffic_delay_estimate)

Start with just distance + availability; add weights only if time permits.

Path/distance computation — use the Haversine formula for straight-line distance (fast, no API needed) as your baseline, and optionally call a routing API (OpenRouteService, free tier) for real driving-time if you have internet access at the venue — this upgrades "distance" to "ETA," which is much more impressive.
Matching as a graph problem — model it as a bipartite graph: patients/requests on one side, hospitals on the other, edges weighted by score. For a single request, this reduces to "find max-weight edge among valid candidates" (easy). For the stretch goal — multiple simultaneous requests competing for the same scarce resource — this becomes the Hungarian Algorithm / assignment problem, which is a great thing to mention even if you only get the simple version working; it shows you understand the harder version of the problem.
Data model (PostgreSQL)
sql
hospitals(id, name, lat, lng, phone, type)
inventory(id, hospital_id, resource_type ENUM('ICU','GENERAL_BED','BLOOD_A+','BLOOD_O-',...), quantity, last_updated)
requests(id, patient_name, resource_type, urgency, lat, lng, status, created_at)
matches(id, request_id, hospital_id, score, distance_km, status, matched_at)

Keep it flat and simple — this is not the place to over-normalize.

Tech stack (fastest path in 12 hours)
Backend: Python FastAPI + Uvicorn (you already know this stack)
DB: PostgreSQL, or even SQLite if Postgres setup eats time you don't have
Frontend: React + Tailwind, with Leaflet.js (free, no API key) or Google Maps JS API for the live map
Real-time updates: WebSockets (FastAPI supports natively) so the dashboard updates live when inventory changes — this is a great demo beat
Distance/routing: Haversine formula in Python (no dependency), OpenRouteService as a stretch goal
